## 2. 完整股池流转机制

- 状态：待处理
- 记录时间：2026-05-05
- 优先级：高

### 背景

当前已落地的是“最小可用股池”：

- 一句话选股结果可勾选后加入本地股池
- 股池具备 `pool_type` 字段
- 股池内股票保留了来源模块、来源查询和来源 run_id
- 监听策略已具备独立事件触发能力，但尚未与股池流转联动

后续目标不是简单的“触发预警后自动加入一个股池”，而是把监听模块、股池模块、自选股模块串成一个统一的“事件驱动流转系统”。

### 已对齐的业务约束

- 股票可以同时存在于多个股池
- 代码层面不强行设计股池层级，但业务上允许存在“信号池 / 确认池 / 择时池 / 自选池”等不同角色
- 流转以“移动”为主，但不是全局唯一归属，允许按规则保留在其他池中
- 同一只股票在同一天内只允许自动流转一次
- 每次流转都必须记录来源事件、来源策略、进入原因
- 需要区分“自动流转”和“人工操作”
- 一个监听策略允许配置多个流转动作
- 流转动作模型对所有监听策略统一，策略本身只负责“是否触发”

### 推荐架构

建议按以下四层拆开，而不是把“进股池”逻辑写死在某个监听策略中：

1. 监听事件层

- 当股票触发监听时，先记录一条标准化事件
- 建议字段：
  - `event_id`
  - `ts_code`
  - `strategy_type`
  - `trigger_type`
  - `trigger_time`
  - `trigger_price`
  - `message`
  - `params_snapshot`

2. 流转规则层

- 单独存储“某类监听触发后应该如何流转”
- 一个策略可配置多个动作
- 建议字段：
  - `rule_id`
  - `strategy_type`
  - `enabled`
  - `from_pool_ids`
  - `to_pool_id`
  - `mode`：`move | copy`
  - `cooldown_days`：默认 `1`
  - `conditions`
  - `priority`

3. 流转执行层

- 监听触发后，不直接修改股池
- 统一交给执行器判断：
  - 今天是否已经自动流转过
  - 当前是否已在目标池
  - 是否需要从来源池移出
  - 是否需要保留在其他池
  - 是否需要同时发送企业微信通知

4. 流转日志层

- 单独记录每次流转，便于追踪与审计
- 建议新增集合：`pool_transition_logs`
- 建议字段：
  - `transition_id`
  - `event_id`
  - `rule_id`
  - `ts_code`
  - `strategy_type`
  - `action_type`
  - `from_pool_ids`
  - `to_pool_id`
  - `operator_type`：`auto | manual`
  - `status`
  - `reason`
  - `created_at`

### 推荐数据模型增强

建议后续增强 `stock_pools.stocks[*]` 的元信息，而不是只保留基础来源字段：

- `source_type`
- `source_strategy`
- `source_event_id`
- `operator_type`
- `entered_at`
- `last_transition_at`
- `status`
- `tags`
- `note`

这样后面做“观察期、遗弃标准、人工确认、择时确认”时会更容易扩展。

### 推荐落地顺序

第一阶段：最小可用版

- 为监听策略增加可选动作：`触发时移动到指定股池`
- 支持企业微信通知与股池流转同时进行
- 支持 `1` 天冷却
- 记录自动流转日志

第二阶段：标准版

- 一个策略支持多个流转动作
- 支持来源池限制
- 支持手工流转与自动流转统一记录
- 为股池详情补充来源事件和进入原因展示

第三阶段：完整流转版

- 支持更复杂的条件组合
- 支持更完整的“信号 -> 确认 -> 择时 -> 自选”路径
- 支持遗弃条件、失效条件和回退流转
- 视行情环境引入不同的流转规则模板

### 建议方向

- 先保持当前 `stock_pools` 结构可用，不急着大改已有页面
- 下一步优先补：
  - `listener_trigger_events` 或同等事件集合
  - `pool_transition_logs`
  - 监听后的流转规则配置入口
- 监听策略本身只负责发出标准化触发事件，不直接嵌入复杂流转逻辑

## 5. 将监听策略改造为真正的多用户隔离模式

- 状态：待处理
- 记录时间：2026-05-11
- 优先级：中

### 当前判断

项目当前不是“全局完全单用户”，而是“多数业务已按 `user_id` 隔离，监听策略仍偏全局单实例模式”。

已经明显按用户隔离的模块：

- 自选股 / 用户中心
- 股池管理 / 一句话选股
- 交割单复盘 / 持仓
- 盘感练习
- AI 助手会话
- 分析任务 / 回测任务

这些模块的 API 和数据写入大多已经带有 `user_id`，后续继续扩展多用户能力的代价相对较低。

当前最需要重构的，是监听策略这一块：

- 目前设计仍是“每种策略类型一条全局策略配置”
- 典型表现：
  - `strategy_subscriptions` 目前按 `strategy_type` 查唯一记录
  - 策略参数、监听股票、启停状态不是天然按用户独立
  - 虽然部分记录已开始写入 `user_id`，但整体架构还不是完整多用户版

### 是否可实现

可以实现，而且方向清晰，不是做不到。

### 主要改造点

1. 数据模型

- 将 `strategy_subscriptions` 从“按 `strategy_type` 唯一”改成“按 `user_id + strategy_type` 唯一”
- 运行时状态、单股配置、流转规则、通知机器人选择都需要跟随用户归属

2. Web API

- 获取策略列表时按当前登录用户返回
- 初始化策略、更新参数、增删监听股票都改为用户维度
- 管理员能力如果仍要保留，需要单独定义“是否可代管他人策略”

3. Listener 运行时

- 当前 Listener 节点加载的是全局策略集合
- 后续要改成加载“所有用户的策略实例”
- 同一策略类型会出现多份用户配置，评估与通知都要带用户上下文

4. 前端页面

- 当前策略监听页默认假设“系统里每种策略只有一条”
- 后续如果保持当前交互体验，可以继续做成“每个用户看到自己的那一套”
- 前端改动不算最大，主要复杂度在后端存储和 Listener 执行层

### 代价评估

- 对监听策略模块：中到偏高
- 对全项目其他用户业务：低到中

也就是说：

- 如果只改“监听策略多用户化”，工作量不小，但边界明确
- 如果担心“整个项目将来都要推倒重来”，目前看并不需要

### 建议节奏

如果后面要做，建议按下面顺序推进：

1. 先把 `strategy_subscriptions` 改成按 `user_id + strategy_type` 取数
2. 再改 ListenerNode 的加载与执行模型
3. 最后再补管理员视角和跨用户管理能力

### 备注

- 这一项先记录为待办，等后续有时间再单独开一个重构回合处理

- 增加按股票、按月份、按方向的更细维度统计
- 增加复盘完成率、标签分布、策略/模式归因统计
- 考虑加入持有周期、连续亏损、连续盈利等节奏类指标

### 建议方向

后续考虑将现有模型拆成三层：

1. 策略定义

- 只描述策略本身的判断逻辑和参数
- 不直接绑定提醒方式、监听池或回测任务

2. 策略实例

- 某个具体策略在某个场景下的一次参数化配置
- 可供多个用途复用

3. 策略用途绑定

- 将策略实例绑定到具体用途
- 例如：
  - 监听预警
  - 回测任务
  - 盘后扫描
  - 股池流转触发

### 当前判断

- 这个方向是正确的
- 但属于中到大的结构性重构
- 会影响策略页、`strategy_subscriptions`、listener、backtest 以及后续策略复用链路
- 不适合与当前“提醒频率 / 重复告警”修复混在同一轮处理

### 建议排期

- 先完成当前监听模块稳定性修复
- 再单独按专题推进“策略中心解耦”

### 当前已知待调整点

- 当前第一版自动流转实现中，`来源股池` 仅部分参与“移动时从哪些池中移出”的逻辑。
- 这意味着：如果某条规则已经配置了来源股池，但股票只是被手动加入监听、并不在这些来源池里，当前实现仍可能执行流转。
- 这与当前已对齐的业务预期不一致。

#### 后续需要修正为

- 自动流转规则必须始终存在明确来源
- `来源股池` 应支持多个
- 规则语义应为：
  - 股票当前必须命中这些来源股池中的至少一个
  - 命中后才允许执行流转
- 不再保留“无来源池限制即可直接流转”的默认路径

- 将该问题视为后续必须处理的流转规则语义修正项
