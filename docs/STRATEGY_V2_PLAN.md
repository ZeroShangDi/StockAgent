# Strategy V2 开发排期与任务拆解

## 1. 文档目的

本文档用于约束 `Strategy V2` 的开发节奏，确保后续开发不跑偏。

总原则：

- 旧功能先不动
- 新功能单独建设
- 优先打通主链路
- 大多数辅助能力直接复用现有实现

## 2. 总体阶段

建议拆为七个阶段：

- Phase 0：设计冻结
- Phase 1：后端核心模型
- Phase 2：策略执行内核
- Phase 3：监听任务 V2
- Phase 4：选股任务 V2
- Phase 5：回测 / 模拟交易 V2
- Phase 6：前端 V2 页面
- Phase 7：灰度替换与旧链路收口

## 3. Phase 0：设计冻结

目标：

- 冻结核心边界
- 冻结新旧并行策略
- 冻结数据模型主结构

任务：

- 确认本轮只重构策略、监听、回测/模拟交易
- 确认股池、交割单、多用户、通知复用
- 确认策略纯函数原则
- 确认统一输出协议
- 确认四类任务场景
- 确认状态粒度与参数优先级

产出：

- 功能清单文档
- 数据模型文档
- 页面原型文档
- 本排期文档

## 4. Phase 1：后端核心模型

目标：

- 建立 V2 的最小后端骨架

任务：

- 新建 `strategy_definitions`
- 新建 `scene_tasks`
- 新建 `strategy_state_store`
- 新建 `task_runs`
- 新建 `task_run_items`
- 新建必要索引
- 建基础 CRUD API

建议拆卡：

- 卡 1：定义 Pydantic 模型
- 卡 2：定义 Mongo 索引
- 卡 3：实现任务 CRUD API
- 卡 4：实现运行记录查询 API

完成标准：

- 可以创建任务
- 可以查询任务
- 可以查询运行记录

## 5. Phase 2：策略执行内核

目标：

- 建立统一策略执行协议

任务：

- 抽象 V2 策略接口
- 定义统一输入上下文
- 定义统一输出结构
- 实现参数解析
- 实现状态读写
- 迁移 2 到 3 个现有策略做样板

建议首批迁移策略：

- `ma5_buy`
- `fixed_stop_loss`
- `price_change`

原因：

- 覆盖了状态型策略和阈值型策略
- 便于验证“策略纯函数 + 状态外置”的实现是否成立

完成标准：

- 可在同一执行器里运行多个 V2 策略
- 支持单标的参数覆盖
- 支持跨日状态读写

## 6. Phase 3：监听任务 V2

目标：

- 先打通最核心、最接近现有需求的链路

任务：

- 实现监听任务执行器
- 支持个股、股池、持仓组、指数、市场目标范围
- 支持监听频率与触发频率控制
- 支持动作执行器
- 接通知动作
- 接股池流转动作
- 写入触发事件与日志

建议拆卡：

- 卡 1：监听任务运行器
- 卡 2：频率控制模块
- 卡 3：动作执行器
- 卡 4：通知适配
- 卡 5：股池流转适配

完成标准：

- 可创建并运行监听任务
- 可发送通知
- 可写股池流转日志

## 7. Phase 4：选股任务 V2

目标：

- 打通“策略 -> 候选 -> 股池”的主路径

任务：

- 实现全市场扫描
- 实现指定范围扫描
- 实现指定时段扫描
- 输出运行结果列表
- 支持结果加入现有股池

建议拆卡：

- 卡 1：扫描目标构建
- 卡 2：运行结果存储
- 卡 3：结果页接口
- 卡 4：加入股池适配

完成标准：

- 可运行选股任务
- 可查看候选结果
- 可把候选加入现有股池

## 8. Phase 5：回测 / 模拟交易 V2

目标：

- 打通“策略运行 -> 交易结果 -> 现有交割单分析”的闭环

任务：

- 实现回测任务
- 实现模拟交易任务
- 统一交易配置输入
- 产出交易结果
- 关联现有交割单分组

建议拆卡：

- 卡 1：回测运行器
- 卡 2：模拟交易运行器
- 卡 3：交易结果转交割单格式
- 卡 4：交割单分组关联

完成标准：

- 可从任务详情进入现有交割单分析
- 回测与模拟交易结果都能落地

## 9. Phase 6：前端 V2 页面

目标：

- 建立不影响旧系统的 V2 入口

任务：

- 新建策略中心 V2
- 新建场景任务中心 V2
- 新建任务详情页 V2
- 新建运行结果页 V2
- 增加与股池页、交割单页的跳转

建议拆卡：

- 卡 1：V2 路由与菜单入口
- 卡 2：任务中心页面
- 卡 3：任务详情页
- 卡 4：运行结果页
- 卡 5：策略中心页

完成标准：

- 用户可从前端完整走通 V2 主链路

## 10. Phase 7：灰度替换与旧链路收口

目标：

- 用真实使用验证 V2
- 决定旧链路收口节奏

任务：

- 用真实任务运行 V2
- 对照旧监听结果
- 对照旧回测结果
- 校验日志、状态、动作执行是否稳定
- 评估旧 `strategy_subscriptions` 是否可替代

完成标准：

- 新链路稳定可用
- 旧链路下线范围明确

## 11. 建议实施顺序

推荐实际开发顺序：

1. Phase 1
2. Phase 2
3. Phase 3
4. Phase 4
5. Phase 6 中与监听相关页面
6. Phase 5
7. Phase 6 中与回测/模拟交易相关页面
8. Phase 7

说明：

- 监听任务是最贴近当前痛点的，优先级最高
- 选股任务次之，因为它直接和股池主路径相关
- 回测 / 模拟交易在接口层可稍后接入，但模型应提前预留

## 12. 关键风险点

### 12.1 旧模型干扰新模型

风险：

- 开发时容易忍不住继续沿用 `strategy_subscriptions` 做中心

约束：

- V2 核心必须以 `scene_tasks` 为中心

### 12.2 策略逻辑和动作逻辑耦合

风险：

- 容易在策略内部直接写股池流转、通知逻辑

约束：

- 策略只输出信号
- 动作由任务执行器处理

### 12.3 回测结果与交割单体系对接不顺

风险：

- 回测结果格式与现有交割单记录口径不一致

约束：

- 早期就明确“运行结果转交割单格式”的映射层

### 12.4 页面入口混乱

风险：

- 旧页面和 V2 页面同时存在时，用户容易混淆

约束：

- V2 初期使用独立入口和独立文案

## 13. 本轮完成后的理想状态

完成本轮后，希望达到：

- 新系统已经能独立承担策略相关核心工作
- 旧系统仍可正常使用
- 股池、交割单、多用户等外围能力已被新系统成功复用
- 后续只需要继续迁移和替换，而不是重新推翻设计
